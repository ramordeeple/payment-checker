# CBR Rates Mock

Детерминированный HTTP-мок метода ЦБ РФ `XML_daily.asp` для end-to-end тестов оплаты зарубежных сервисов.

Сервис не обращается к ЦБ и не проверяет платежи. Он возвращает заранее подготовленный XML с курсами валют, а платёжная система использует этот ответ для расчёта суммы в рублях и проверки лимита `15 000 ₽`.

## API

```http
GET /scripts/XML_daily.asp?date_req=DD/MM/YYYY
```

Для даты `02/03/2002` сервис возвращает фикстуру с курсом:

```xml
<ValCurs Date="02.03.2002" name="Foreign Currency Market">
    <Valute ID="R01235">
        <NumCode>840</NumCode>
        <CharCode>USD</CharCode>
        <Nominal>1</Nominal>
        <Name>Доллар США</Name>
        <Value>75,0000</Value>
    </Valute>
</ValCurs>
```

Возможные ответы:

| Условие | Статус |
|---|---:|
| Дата существует в наборе фикстур | `200 OK` |
| Параметр `date_req` отсутствует | `400 Bad Request` |
| Дата передана не в формате `DD/MM/YYYY` | `400 Bad Request` |
| Для даты нет фикстуры | `404 Not Found` |
| Использован метод, отличный от GET | `405 Method Not Allowed` |

Готовые ручные запросы находятся в [`requests/mock.http`](requests/mock.http).

## Тестовые сценарии для лимита

Фикстура на `02/03/2002` задаёт курс `1 USD = 75 ₽`. Сумма платежа в рублях рассчитывается платёжной системой:

```text
amount_rub = amount * value / nominal
```

Это позволяет проверить границу лимита без изменения состояния мока:

| Сумма платежа | Сумма в рублях | Ожидаемый результат платёжной системы |
|---:|---:|---|
| `199.99 USD` | `14 999.25 ₽` | платёж разрешён |
| `200.00 USD` | `15 000.00 ₽` | платёж разрешён |
| `200.01 USD` | `15 000.75 ₽` | платёж запрещён |

По условию запрещена сумма **более** `15 000 ₽`, поэтому сама граница допустима. Мок только отдаёт курс; решение о допустимости платежа остаётся ответственностью тестируемой платёжной системы.

## Почему используются XML-фикстуры

Фикстуры хранятся в `internal/cbr/fixtures` и встраиваются в бинарник через `embed`.

- Воспроизводимость: дата всегда соответствует одному и тому же ответу.
- Надёжность: тесты не зависят от доступности ЦБ, сети или общего состояния БД.
- Параллельность: сервис не изменяет состояние, поэтому запросы сотен тестов не влияют друг на друга.
- Гибкость: разные сценарии задаются разными датами из настоящего контракта ЦБ, без служебных заголовков и параметров управления моком.

Чтобы добавить сценарий, нужно создать файл `internal/cbr/fixtures/YYYY-MM-DD.xml` и пересобрать приложение. Например, запросу `date_req=03/03/2002` соответствует файл `2002-03-03.xml`.

База данных намеренно не используется: для неизменяемого набора тестовых курсов она добавила бы общее изменяемое состояние и усложнила параллельные тесты. Если в будущем потребуется менять набор сценариев без пересборки образа, хранение версионированных наборов данных можно вынести во внешнее хранилище.

## Запуск

### Локально

Требуется Go 1.25 или новее.

```shell
go run ./cmd/payment-checker
```

При установленном [Task](https://taskfile.dev/):

```shell
task run
```

По умолчанию сервис доступен на `http://localhost:8080`. Внутренний порт можно изменить переменной окружения `REST_API_PORT`.

### Docker Compose

Требуется Docker с поддержкой Compose.

```shell
task docker-up
```

Compose читает внешний порт из `.env.local`. Остановить окружение из другого терминала:

```shell
task docker-down
```

Проверить итоговую конфигурацию Compose без запуска контейнера:

```shell
task docker-config
```

## Проверки

Запустить тесты и статический анализ:

```shell
task check
```

Отдельные команды:

```shell
task test
task vet
task build
```

Тесты проверяют успешный ответ, валидность и структуру XML, ошибки входных данных и одновременное выполнение ста запросов.
